# MONTESSORI — AGENTS.md

## PROJECT IDENTITY

Project name: MONTESSORI

Slogan:
"Keşfet. Dene. Öğren. Hayal Et."

Purpose:
This is a non-commercial child learning project.

The sole purpose is to provide children who are beginning to discover reading, writing, numbers and the world with a safe, enjoyable, modern, accessible and genuinely useful learning environment.

Core principle:

CHILD FIRST
EDUCATION SECOND
SAFETY THIRD
EXPERIENCE FOURTH
TECHNOLOGY LAST

Technology must serve the child's learning experience and never become the purpose itself.


## CORE ETHICAL PRINCIPLE

The application must never attempt to maximize screen time.

The application must never intentionally create dependency, compulsive use or psychological pressure.

The desired loop is:

CURIOSITY
→ DISCOVERY
→ TRY
→ SUCCESS
→ LEARNING
→ NEW CURIOSITY

Never optimize the child for engagement duration.

Optimize only for learning value, autonomy, safety and meaningful discovery.


## TARGET USERS

Primary audience:

Children approximately 4–8 years old who are beginning to learn:

- letters
- phonemes
- reading
- writing
- numbers
- counting
- basic mathematics
- shapes
- colors
- memory
- attention
- logic
- creativity
- science
- nature
- stories

Age must never be treated as a direct proxy for ability.

Learning should progressively adapt to demonstrated skill.


## PEDAGOGICAL PRINCIPLES

Every activity must answer:

"Does this activity teach or strengthen a meaningful skill?"

If the answer is no, redesign or remove it.

Avoid activity patterns that merely require tapping without meaningful cognitive value.

Learning should progress from:

CONCRETE
→ VISUAL
→ INTERACTIVE
→ ABSTRACT

Example:

objects
→ quantity
→ numeral
→ written number word

Do not introduce unnecessary cognitive complexity.


## CHILD AUTONOMY

The child should be able to:

- repeat
- pause
- leave
- choose another activity
- request help
- proceed at their own pace

Never force progression.

Never create fear of missing out.

Never punish leaving an activity.


## FORBIDDEN ENGAGEMENT MECHANICS

Never implement:

- infinite scrolling
- aggressive notifications
- streak pressure
- countdown pressure without educational justification
- fear of losing progress
- manipulative rewards
- dark patterns
- forced continuation
- forced repetition
- child-targeted advertising
- purchases
- subscriptions
- monetization pressure

Rewards may exist only when they reinforce meaningful discovery.

The application must never imply:

"Stay longer to win."

It should communicate:

"Discover something new."


## CHILD SAFETY

Default principles:

- no advertising
- no social network
- no public profiles
- no strangers
- no child-to-child communication
- no unnecessary location access
- no unnecessary camera access
- no unnecessary microphone access
- no unnecessary personal information
- no unnecessary tracking
- no unnecessary analytics

Never collect information that is not necessary for learning functionality.


## AI SAFETY

If AI is introduced later:

AI must never:

- encourage emotional dependency
- claim to need the child
- ask the child to keep secrets
- encourage secrecy from parents
- request unnecessary personal information
- manipulate the child
- frighten the child
- replace the child's thinking
- encourage prolonged usage

AI may assist with:

- educational explanations
- teacher support
- parent reports
- content generation
- learning adaptation
- accessibility
- carefully constrained educational assistance

## TOUCH TARGETS

Minimum:

44 × 44 px

Preferred:

52–64 px

## RESPONSIVE DESIGN

Priority:

1. Phone
2. Tablet
3. Desktop

Tablet should provide additional educational workspace.

No content may overflow or become unusable on supported screen sizes.


## UX PRINCIPLES

Every interaction must communicate clearly that it happened.

Possible feedback:

- visual response
- subtle animation
- optional sound
- optional haptic feedback

Feedback must remain calm and short.

The child should never wonder:

"Did my tap work?"


## ANIMATION

Preferred interaction duration:

150–350ms

Animations must be:

- short
- smooth
- purposeful
- performant

Do not animate everything.

Respect:

prefers-reduced-motion


## ACCESSIBILITY

- large text
- high contrast
- audio assistance
- reduced motion
- keyboard navigation
- touch interaction
- screen-reader semantics
- color-independent information

Accessibility is not an optional enhancement.

## WRITING ENGINE

Writing should support:

- Guided
- Assisted
- Independent

Writing feedback must be supportive.

The system may analyze:

- path completion
- direction
- approximate shape
- completion consistency

Do not present pseudo-precise educational judgments from weak heuristics.


## AUDIO

Audio should be:

- short
- calm
- clear
- optional where appropriate

Provide an obvious audio control.

Do not continuously play sounds.

Provide mute controls.

Audio must not block the core learning experience when unavailable.

## STORIES

Stories should be:

- calm

- age appropriate

## CREATIVITY

## PROGRESS

Progress must be learning-centered.

Do not prioritize:

"47 minutes played"

Prefer:

"8 letters recognized correctly."

"B may benefit from additional review."

"Counting from 1–10 is developing."

Child-facing progress should be visual and simple.

Parent-facing progress may contain more detail.


## PARENT AREA

Child Mode and Parent Mode must be clearly separated.

Child Mode:

- simple
- safe
- minimal
- no technical information
- no developer controls

Parent Mode may contain:

- learning progress
- learned letters
- learned words
- mathematics progress
- activity history
- areas needing review
- accessibility settings
- content controls
- export/import
- screen-time controls
- sleep-time controls

Parent access must not be exposed through a simple accidental icon tap.

Use an appropriate parent gate.


## DATA ARCHITECTURE

Default principle:

LOCAL-FIRST

Prefer local storage for educational state.

Do not send child learning data to a server unless there is a clearly justified requirement.

Collect the minimum necessary data.

Do not introduce analytics merely because analytics are technically available.


## OFFLINE-FIRST

Core functionality should work offline.

At minimum, offline operation should support:

- letters
- basic activities
- basic mathematics
- saved progress

The application must fail gracefully when network resources are unavailable.

## DEVELOPMENT PROTOCOL

Before modifying an existing repository:

PHASE 1 — INSPECT

Read and understand the repository.

Never modify code before understanding the current architecture.

PHASE 2 — PLAN

Document:

- current architecture
- problem
- proposed solution
- affected files
- risks
- test plan

PHASE 3 — IMPLEMENT

Implement the approved plan.

PHASE 4 — TEST

Run appropriate tests.

PHASE 5 — REVIEW

Read the changed code again.

PHASE 6 — UX REVIEW

Review from the perspective of a first-time child user.

PHASE 7 — ACCESSIBILITY REVIEW

Review accessibility.

PHASE 8 — PERFORMANCE REVIEW

Review performance.

PHASE 9 — SECURITY REVIEW

Review security and child safety.

PHASE 10 — FINAL

Run:

git diff --check
git status

Then perform regression testing.


## BUILD → TEST → VERIFY

Never consider a feature complete merely because the code looks correct.

If a button is added:

Test the button.

If navigation is added:

Test navigation.

If a game is added:

Play through the complete game.

If audio is added:

Test loading and playback.

If responsive design is changed:

Test phone, tablet and desktop layouts.

If offline functionality is changed:

Test with network unavailable.


## QUALITY QUESTIONS

For every completed screen ask:

1. Does a child understand what to do?
2. Is there visual clutter?
3. Is the primary action obvious?
4. Is text readable?
5. Are touch targets large enough?
6. Is color appropriate?
7. Is animation necessary?
8. What happens when the child makes a mistake?
9. What happens when the child succeeds?
10. Does the screen genuinely contribute to learning?


## CHILD INDEPENDENCE TEST

Ask:

"Can a first-time five-year-old understand what to do without adult assistance?"

If no:

Redesign the experience.


## PEDAGOGICAL TEST

Ask:

"Does the child gain a meaningful skill here, or are they merely touching the screen?"

If the activity is primarily meaningless interaction:

Redesign it.


## ERROR HANDLING

Never expose technical errors to children.

Never show:

"JavaScript Error"

Instead:

"Bir şeyler ters gitti. Tekrar deneyelim."

Technical details may be available only in appropriate developer/parent contexts.
